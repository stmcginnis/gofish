# Schema generator

`generate-schemas` writes the Go types in `schemas/` and `serviceroot.go` from
the DMTF Redfish and SNIA Swordfish JSON schema bundles. Generated files start
with `// Code generated by generate-schemas. DO NOT EDIT.` Never edit them;
every change goes through the generator config or a hand-written file, so a
regeneration never loses it.

## Regenerating

The bundle versions are pinned in the top-level `Makefile`:

```bash
make generate                                   # pinned REDFISH_TAG / SWORDFISH_TAG
make generate REDFISH_TAG=2026.3 SWORDFISH_TAG=v1.3.0_Release
make check-generate                             # fails if the committed output is stale
```

To move to a new bundle:

1. Bump `REDFISH_TAG` and `SWORDFISH_TAG` in the `Makefile` and run `make generate`.
2. Read every `WARNING:` line the generator prints. Each one is a definition
   that two schemas define differently and that would be merged into one Go
   type. Resolve it with a `TypeRenames` or `TypeOwners` entry (below).
3. Run `go build ./...`, `go vet ./...` and `make test`. A compile error after
   a bump is usually an upstream change that collides with a hand-written
   declaration or field override; fix the config or the `*_custom.go` file,
   not the generated file.
4. Check the exported API against the previous release, for example with
   `golang.org/x/exp/cmd/apidiff`. Upstream changes can break callers: a fourth
   action parameter switches the method to a parameter struct, and a changed
   property type changes the field type. Decide whether to accept the break or
   pin the old shape with a field override.
5. Commit the `Makefile` bump, any config changes and the regenerated files
   together. CI runs `make check-generate`, so a generator change without its
   regenerated output fails the build.

`--local dir1,dir2` generates from checked-out bundles instead of cloning.
Swordfish is recognized by its directory path, so the Swordfish directory name
must contain `swordfish`. `-object Name` generates one schema without the
cross-schema steps below; use it for debugging only.

## Customizing generated code

There are two places to change the output. Prefer config for anything that is a
naming or typing decision, and a hand-written file for behavior.

### Generator config (`internal/config/config.go`)

| Setting | Use it to |
|---|---|
| `TypeRenames` | Give a definition a schema-specific Go name, keyed `"Schema.Definition"`. All definitions share one package, so this resolves name collisions such as `Settings.ApplyTime` and `UpdateService.ApplyTime`. References from every schema use the new name. |
| `TypeOwners` | Pick the schema that emits a type more than one schema defines. Other copies are dropped and their enum values are merged into the owner's. An entry also marks a differing copy as reviewed, which silences its warning. |
| `SkipDefinitions` | Drop a definition entirely, keyed `"Schema.Definition"`. |
| `FieldOverrides` | Replace a generated field declaration, keyed `"Type.field"` by Go names, or drop it with `""`. Works for schema properties, `Links` fields, action target fields and action parameter struct fields. The overridden field gets no link handling or getter, so the type usually needs a hand-written `UnmarshalJSON`. |
| `ExtraFields` | Append hand-maintained fields to a generated struct or parameter struct. Hand-written code populates them. |
| `LenientFields` | Decode a field through a converter, keyed `"Type.Field"`, for vendors that send the wrong JSON type (a number as a string, an object where the schema has an array). The converter is a `func(any) T` in package `schemas`: `toInt`, `toFloat32`, `toFloat64` and `parseString` in `utils.go`, or a type-specific one in the type's `*_custom.go`. |
| `PluralNames` | Override the `<Type>s` plural in `ListReferenced<Plural>`. |
| `NonLinkTypes` (`internal/parser/typemapper.go`) | Treat a property as an embedded object rather than a link. |

### Hand-written files

Hand-written Go files in `schemas/` (and the repo root for `serviceroot.go`)
replace or extend generated code. The generator scans every file without the
generated marker and does not emit any type, function, method or constant
declared there. To change a generated method, copy it into the matching
`<schema>_custom.go`, edit it there, and regenerate; the generated copy
disappears.

To decode more than the generated `UnmarshalJSON` does, define a
`postUnmarshal` hook instead of replacing `UnmarshalJSON`:

```go
// postUnmarshal records the allowed reset types.
func (c *Chassis) postUnmarshal(b []byte) error {
	var t struct {
		Actions struct {
			Reset struct {
				AllowedResetTypes []ResetType `json:"ResetType@Redfish.AllowableValues"`
			} `json:"#Chassis.Reset"`
		}
	}
	if err := json.Unmarshal(b, &t); err != nil {
		return err
	}
	c.SupportedResetTypes = t.Actions.Reset.AllowedResetTypes
	return nil
}
```

The generated `UnmarshalJSON` decodes the type, fills every link and action
target, and then returns `postUnmarshal(b)`. Links and actions that later
schema versions add keep working without touching the hook. A link property
overridden to `string` or `[]string` is skipped by the generated decode, so the
hook must fill it.

When a vendor sends a field with the wrong JSON type, add a `LenientFields`
entry rather than replacing `UnmarshalJSON`; the rest of the type keeps its
generated decoding. Replace `UnmarshalJSON` only when the payload is wrong as a
whole, such as `IPMIHostInterface` sent as a bare bool or `PCIeInterface` sent
as `[]`. A replacement has to fill every link and action target itself and
does not pick up ones added by later schema versions, so keep replacements to
types without links.

Every vendor workaround needs a test that decodes the vendor's payload and
checks the corrected values, so a regeneration or refactor that drops it fails
a test.
